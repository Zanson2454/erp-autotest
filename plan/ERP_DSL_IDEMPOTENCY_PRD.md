## 2. 背景与问题定义
当前 ERP 自动化框架存在以下核心问题：
1. 用例层业务语义弱，存在大量低层 API 调用拼装，维护成本高。
2. 造数过程非幂等，重复执行常导致环境污染与状态竞争。
3. 测试间互相调用（`self.test_xxx()`）与顺序依赖导致 flaky。
4. 新成员对 API 字典依赖重，编写完整链路学习成本高。

## 3. 项目目标
1. 建立统一 Flow 协议（Domain DSL），将高频业务动作语义化封装。
2. 建立 Ensure 幂等造数能力，支持“先查后建 + 并发兜底”。
3. 在不破坏现有回归能力的前提下，分批替换遗留调用模式。

## 4. 成功指标（KPI）与计算口径
1. SLOC 收敛: 同等业务覆盖下，`testcases/` 代码行数下降 >= 40%。
2. Flaky 下降: 环境/顺序/竞争导致 flaky 占比 < 1%。
3. Setup 耗时下降: 同用例二次执行的 Setup 耗时下降 >= 70%。
4. 上手效率: 新同学 30 分钟内可基于 Flow 完成“采购到入库”链路脚本。
5. Agent Ready: Flow 方法具备完整中文 Docstring，LLM 可正确生成调用参数。

口径约束：
1. 基线采集日固定为 2026-04-03。
2. 对比数据必须使用同环境、同数据集、同并发参数。
3. 报告统一归档至 `outputs/` 与 `outputs/gates/`。
4. Flaky 计算公式固定为: `flaky_rate = flaky_failures / total_case_executions`。
5. `total_case_executions` 为统计窗口内全部用例执行次数，不因首次失败提前中断。
6. Setup 计算口径固定为: `setup_gain = (baseline_setup_p50 - rerun_setup_p50) / baseline_setup_p50`。
7. `flaky_failures` 判定规则:
   - 同一 `nodeid` 在统计窗口内“至少一次失败且后续通过”计为 1 条 flaky case。
   - 同一 `nodeid` 多次抖动仅计 1，不重复累加 case 数。
   - 环境不可用、网络中断、人工中止不计入 flaky，单独归入 `infra_failures`。

## 5. 范围定义
### 5.1 In Scope（本期）
1. `BaseFlow` 协议、异常语义、返回对象规范。
2. `TestContext` 并发隔离与用例生命周期管理。
3. MDM 只读 Repository（组织/物料查询）。
4. `ensure_org_exists`、`ensure_material_exists` 幂等能力。
5. `ensure_*` fixture 注入化。
6. 采购/销售/库存三条高频链路 DSL 试点。
7. 首批遗留互调与直接 HTTP 调用替换。

### 5.2 Out of Scope（本期不做）
1. 全仓一次性改造 613 处历史调用。
2. `erp_data_factory/legacy` 立即物理删除。
3. 与专项目标无关的大规模框架重构。

## 6. 业务角色与使用场景
1. 自动化测试工程师: 使用 Flow 快速构建链路并断言业务结果。
2. 框架维护者: 维护 DSL 协议与 Ensure 行为的一致性。
3. 新成员: 通过 Flow 文档与示例快速完成业务编排。

关键场景：
1. 冷启动环境执行核心回归，系统自动补齐最小业务前置数据。
2. 既有环境二次重跑时，Ensure 自动复用数据而非重复创建。
3. 并发执行采购与销售链路时，Context 无跨用例污染。

## 8. 非功能需求
1. 稳定性: 并发下无上下文串扰与重复造数。
2. 可观测性: 关键步骤记录到 Allure，失败路径可追踪。
3. 可维护性: Flow 层 API 命名语义化，文档可直接用于新成员 onboarding。
4. 向后兼容: 采用分批灰度替换，保留回滚开关与旧入口。

## 9. 依赖与约束
1. 依赖 `standard_api_call` 作为统一 API 调用基座。
2. 依赖数据库唯一键或业务唯一性校验支持幂等兜底。
3. 依赖 pytest/xdist 执行模型，需验证进程级隔离策略。
4. 严格遵守项目规则：禁止测试互调、禁止 SQL 字符串拼接、禁止硬编码测试数据。

## 10. 验收标准（业务视角）
1. W0 完成后，`outputs/` 中可看到完整基线与 Gate 模板产物。
2. W2 完成后，同参数 ensure 连续调用不新增数据，且并发调用稳定。
3. W3 完成后，三条链路可通过一层 Flow 编排并输出业务对象断言。
4. W4 完成后，完成首批迁移、专项回归、指标对比报告。
5. 指标报告必须包含统计窗口、分母定义、失败明细与原始命令。

## 11. 发布与推广策略
1. 先在 `dsl_pilot` 标记场景灰度启用。
2. 每周 Gate 通过后扩大替换批次。
3. 新功能默认走 Flow + Ensure；旧模式只允许修复不允许扩写。

## 12. 风险与应对
1. 抽象过度风险: 只封装高频稳定动作，不做大一统编排引擎。
2. 并发脏写风险: 冲突后回查 + 并发回归作为准入门槛。
3. 迁移回归风险: 按模块分批替换并保留回滚路径。
4. 指标失真风险: 固定采集命令与环境，禁止人工二次加工。
