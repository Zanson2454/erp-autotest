# 接口测试规范

> 适用范围：本规范适用于本项目所有ERP核心业务（采购-库存-销售）相关接口的自动化测试。

---

## 1. 测试分层与自动化原则

- **分层设计**：推荐分为基础数据层、接口服务层、业务流程层，必要时可增加模块测试层。接口测试应覆盖端到端主流程，兼顾各业务域独立性。
- **AIR原则**：
  - **A（Automatable）全自动化**：测试用例应全自动、无人工干预，适合高频回归。
  - **I（Independent）独立性**：用例间无依赖，环境、数据、账号等均隔离。
  - **R（Repeatable）可重复**：多次执行结果一致，避免偶发性失败。

---

## 2. 目录结构与用例组织

- 所有接口测试用例统一放置于 `testcases/` 目录下，按业务域（如`sls`销售、`crm`客户、`comm`通用等）分子目录管理。
- 通用基类、断言工具、数据工厂等放于 `testcases/comm/`、`utils/` 等目录，便于复用。
- 测试用例文件命名采用 `test_XX_业务描述.py`，类名采用 `Test业务_功能`，方法名采用 `test_功能描述`。

---

## 3. 命名规范

- **测试空间命名**：产品名+版本号（如SCM_V1.0.0），大版本切换需新建空间。
- **业务场景集命名**：首级固定，后续用"-"分隔，便于平铺管理。
- **业务场景命名**：子模块_场景名，突出业务语义，避免冗余，场景名唯一。
- **接口命名**：主语+动词+名词+断言（如"用户订购商品_成功"），简洁明了。
- **参数命名**：
  - 全局参数：统一前缀（如configs.autotest.**）
  - 公共入参/出参：带业务域前缀，便于数据清理和追溯
  - 业务域内参数：简洁明了，建议单据类数据带Auto_前缀

---

## 4. 测试用例编写规范

- **Allure 标注**：
  - 用例需使用 `@allure.epic`、`@allure.feature`、`@allure.story` 标注业务域、功能模块、用户场景。
  - 关键步骤用 `with allure.step("步骤描述")` 明确标注。
  - 用例优先级用 `@allure.severity` 标注。
- **Pytest 结构**：
  - 每个测试类专注单一功能点，方法粒度清晰。
  - 支持参数化（`@pytest.mark.parametrize`）实现数据驱动。
- **断言规范**：
  - 统一使用 `AssertHelper` 工具类断言接口响应、数据完整性、业务逻辑。
  - 断言失败时自动附加页面截图（通过pytest钩子或Allure附件实现）。
- **数据准备与隔离**：
  - 测试数据生成采用工厂模式（如`MockData`、`Faker`等），避免硬编码。
  - 用例间数据隔离，避免相互依赖。
- **环境配置**：
  - 所有环境变量、敏感信息通过 `.env` 文件集中管理。
  - 不同环境下测试数据、配置严格隔离。

---

## 5. 异步交互、Cookie与参数引用

- **异步接口**：
  - 明确等待时间（如5s），每次异步后需校验实际结果与预期一致。
  - 支持循环轮询，建议配置最大循环次数、间隔、衰退策略，结束条件以断言为准。
- **Cookie保持**：
  - 登录接口返回Set-Cookie后，自动续传至同一场景后续接口。
  - 不支持跨场景Cookie续传，多个登录接口时取最近一次。
- **参数引用**：
  - 全局变量、场景入参、其他场景出参、随机值等均有统一格式，便于数据流转与清理。
  - 建议公共场景出参带业务域前缀，便于追溯。

---

## 6. 断言与错误处理标准

- **断言细则**：
  - 所有接口都需断言，避免仅校验200或空校验。
  - 推荐code、msg正确性校验，必要时结合数据库校验。
  - 新建-编辑-查询-删除等多步场景，需传递ID并校验数据一致性。
  - 删除后通过ID查询或列表total对比，确保数据已删除。
- **断言工具支持**：
  - 响应状态/码/消息校验
  - 关键字段存在性校验
  - 列表非空、长度、范围校验
  - 业务ID、唯一性、数据一致性校验
- **错误处理**：
  - 统一异常处理装饰器（如 `@safe_api_call`），自动捕获并上报异常。
  - 失败时详细记录请求、响应、上下文信息，便于追溯。

---

## 7. 循环策略与异步轮询

- 支持异步接口的自动轮询，配置最大循环次数、间隔、衰退比例等。
- 结束条件建议以断言为主，支持多条件组合。
- 典型场景如：异步任务状态、数据准备多次执行等。

---

## 8. 测试环境与数据隔离

- 测试环境与生产环境严格隔离，所有接口测试仅在测试环境执行。
- 测试用例需具备幂等性，避免对真实业务数据造成影响。
- 数据初始化、清理通过基类或专用工具自动完成。

---

## 9. 追溯机制与文档化

- 每个测试用例需关联业务需求编号（可通过Allure标签或注释实现）。
- 测试资产与业务需求双向追溯，便于覆盖率统计与缺陷定位。
- 所有接口、用例、数据结构需有详细注释与文档说明。

---

## 10. 执行计划与通知模板

- 支持日常全量自动化、定时回归、流水线触发等多种执行方式。
- 可配置通知模板，自动推送测试结果至相关负责人。
- 参考[pipeline.yml](https://terminuscloud.yuque.com/attachments/yuque/0/2024/yml/2515264/1731913212358-9b175502-e577-450f-9cf0-ddf24c13aa15.yml)实现自动化通知。

---

## 11. 覆盖率统计与Q&A

- 推荐结合平台工具统计接口测试覆盖率，持续提升主流程与核心场景的自动化覆盖。
- 参考[官方文档](https://docs.erda.cloud/next/manual/dop/guides/qa-and-testing/e2e-code-coverage.html#%E4%BB%A3%E7%A0%81%E8%A6%86%E7%9B%96%E7%8E%87%E7%BB%9F%E8%AE%A1)进行覆盖率统计。
- 常见问题：
  1. 业务域基础数据可独立拆分，减少依赖与引用时间。
  2. 删除用户、数据等需考虑审批流与下游依赖，建议域内实现删除并及时清理。
  3. 增删改查无下游依赖的数据建议自动清理，保障环境整洁。

## 12. 参考示例

```python
import pytest
import allure
from testcases.comm.base_test import BaseTest

@allure.epic("进销存管理")
@allure.feature("订单管理")
class TestOrderCreate(BaseTest):
    @allure.story("供应商订单创建")
    @allure.severity(allure.severity_level.CRITICAL)
    @pytest.mark.parametrize("supplier_type, discount", [
        ("战略", 0.8), ("普通", 1.0)
    ], ids=["战略供应商8折", "普通供应商无折扣"])
    def test_create_supplier_order(self, supplier_type, discount):
        """验证不同供应商类型的折扣计算逻辑"""
        with allure.step("前置条件：登录采购账号"):
            self.login(role="purchaser")
        with allure.step("创建供应商订单"):
            order = self.create_order(supplier_type=supplier_type)
        with allure.step("验证折扣率"):
            self.assert_util.assert_value_in_range(order.discount, discount, discount, "折扣计算")
```
