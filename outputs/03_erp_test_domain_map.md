# ERP API TEST DOMAIN MAP（2026-03-31 更新）

## 1. Master Data（主数据）
**Test Goal**: 验证主数据的 CRUD 正确性，数据隔离（AT_ 前缀），依赖初始化缓存。

| 维度 | 说明 |
|---|---|
| 前置条件 | `init_data`（币种/国家/地址/银行）、`md_cache_data`（合作伙伴/组织/物料）已初始化 |
| 关键断言点 | 保存响应含 ID、DB 中记录存在、code 含 AT_ 前缀、enable/disable 状态流转正确 |
| 风险点 | 缓存命中失败时 `bind_cache_data` 返回 None 导致接口传参错误但无明显报错 |
| 测试级别 | smoke + regression |
| 当前覆盖 | `gen_md`（gen_base/org/mat/partner/todo）：覆盖完整；其他主数据模块待确认 |

## 2. Document APIs（单据类）
**Test Goal**: 验证单据创建→提交→审批→执行→关闭的完整生命周期，以及异常分支。

| 维度 | 说明 |
|---|---|
| 前置条件 | 主数据就绪、权限配置正确、相关业务配置已初始化 |
| 关键断言点 | 单据状态字段在每步操作后正确流转、关联明细记录完整、DB 状态与响应一致 |
| 风险点 | 状态依赖上一步，用例串行顺序错误会导致级联失败（需 `file_level_order` 保障） |
| 测试级别 | regression + flow |
| 当前覆盖 | `erp_fin`（fin_iv/fin_ap/fin_ar 等）、`scm_sls`、`scm_pur`、`scm_del`：有覆盖，深度不一 |

## 3. State Transitions（状态流转）
**Test Goal**: 验证业务对象在各状态下的合法/非法操作响应，边界状态防护。

| 维度 | 说明 |
|---|---|
| 前置条件 | 对象处于指定前置状态（需先执行前序操作用例） |
| 关键断言点 | 合法操作：状态字段变更为目标状态；非法操作：返回业务错误码而非 500 |
| 风险点 | 并发执行时前置状态被其他用例修改，导致偶发失败（需加入 `serial_flow` 分组） |
| 测试级别 | regression + exception |
| 当前覆盖 | 部分覆盖，启用/禁用/删除场景较多；审批流/执行态深度覆盖不足 |

## 4. Query / Report（查询/报表）
**Test Goal**: 验证分页查询、字段过滤、条件筛选的正确性，以及空结果边界处理。

| 维度 | 说明 |
|---|---|
| 前置条件 | 目标数据已存在（依赖 save 用例先执行） |
| 关键断言点 | 分页结构正确（`data.data.data` 列表非空）、`needTotal` 有值、筛选条件生效 |
| 风险点 | 用例直接依赖其他测试方法的执行结果，若顺序变化会失败 |
| 测试级别 | smoke + regression |
| 当前覆盖 | 广泛覆盖，几乎每个模块有分页查询用例 |

## 5. Permission / Isolation（权限与数据隔离）
**Test Goal**: 验证多角色下数据可见性隔离，跨租户/跨组织数据不互串。

| 维度 | 说明 |
|---|---|
| 前置条件 | 多门户账号可用（`TERP_PORTAL`/`TERP_CUST_PC`），`module_login_multi_portal` 已初始化 |
| 关键断言点 | 角色A创建的数据对角色B不可见（或只读）；越权操作返回 403/业务拒绝码 |
| 风险点 | 权限深度断言实现率低，多数用例只验证操作成功，未验证数据隔离效果 |
| 测试级别 | regression + permission |
| 当前覆盖 | 有多门户登录封装，但深度权限断言覆盖不足（推断） |

## 6. Idempotency（幂等与重复提交）
**Test Goal**: 验证重复调用创建/关联接口时返回"已存在"错误码并可安全重试。

| 维度 | 说明 |
|---|---|
| 前置条件 | 目标数据已存在（可能因环境重用或物理删除关闭导致） |
| 关键断言点 | 返回 `xxx.is.exist` 错误码时，能回查已有数据并继续断言，而不是直接失败 |
| 风险点 | `ENABLE_PHYSICAL_DELETE=false` 时测试数据无法删除，下次运行直接冲突 |
| 测试级别 | regression |
| 当前覆盖 | 规范有幂等 helper 模板，但现有用例实现覆盖率不均 |

## 7. Multi-role Workflow（多角色协同）
**Test Goal**: 验证跨角色协同操作（如供应商提交 → 运营审批 → 经销商确认）的完整链路。

| 维度 | 说明 |
|---|---|
| 前置条件 | 多角色账号均已登录（`module_login_multi_portal`），相关主数据已关联 |
| 关键断言点 | 每个角色操作后状态流转正确，对方角色可见预期结果 |
| 风险点 | 并发执行会导致角色状态互相干扰（必须 `serial_flow`） |
| 测试级别 | flow + permission |
| 当前覆盖 | `scm_sls`（销售/客户双角色）有覆盖，其他模块待确认 |

## 8. Upstream / Downstream Dependency（上下游依赖）
**Test Goal**: 验证上下游单据/数据的联动正确性（如采购单 → 入库单 → 库存变化）。

| 维度 | 说明 |
|---|---|
| 前置条件 | 上游单据已完成（状态满足下游触发条件），相关配置已就绪 |
| 关键断言点 | 下游数据自动创建或更新，金额/数量计算正确，状态同步一致 |
| 风险点 | 上游用例未执行或失败时下游用例全部级联失败，难以定位根因 |
| 测试级别 | flow + regression |
| 当前覆盖 | 有链路用例（`scm_sls → scm_del`），但跨模块端到端链路覆盖仍不系统 |

## 复审结论（2026-03-31）

**已改善**：
- `gen_md` 清理全面注册化，30+ 张表兜底，含动态列探测（不硬编码列名）。
- `bind_cache_data()` 降低了数据绑定写错路径的风险。
- `__init_subclass__` 兜底保证资源不泄漏。
- 多门户 helper 标准化（`module_login_multi_portal`）。

**仍待解决**：
- P0：`ApiCallService` 仍持有 `test_obj`，并发 `store_id_as` 写类属性不安全。
- P0：25 个模块清理模式未迁移（非 gen_md/scm_sls/scm_del）。
- P1：权限深度断言覆盖率低。
- P1：上下游端到端链路覆盖不系统。
- P2：`bind_cache_data` 路径路由硬编码数据源，扩展需改基类。
